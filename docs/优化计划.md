### 0.5.1 第二轮回归（16:11 / 16:13 logcat 分析结论）

**问题 1（后台接收）**：
- 后台时 `WifiP2pManager.connect()` 直接返回 ERROR，EMUI/HarmonyOS 限制后台 P2P 操作。
- 接收确认页只有在 App 前台时能弹出：`GattServerService` 从后台 Service `startActivity` 被系统拦截。
- 修复：新增 `USE_FULL_SCREEN_INTENT` 权限；BLE 收到对端 P2P 信息后除 `startActivity` 外，同时发布带 `setFullScreenIntent` 的高优先级通知，由系统以全屏方式拉起 `ReceiveConfirmActivity`（通知保留在通知栏作为兜底入口，用户点击同样进入确认页）。

**问题 2（二次发送 BLE 失败）**：
- 16:12 日志：第二次发送 `connectGatt` 成功、MTU 3 秒超时跳过已生效，但 `discoverServices()` 10 秒无回调，两次尝试均超时；对端（OPPO 系统分享）GATT server 会话残留。
- 修复：BLE 握手块 finally 中先 `disconnect()`（等待 300ms）再 `close()`，让对端收到明确的断开通知并释放 GATT server；重试次数 2→3，间隔延长至 2 秒。

**问题 3（分享面板对端不落盘）**：
- 16:14 日志：分享面板链路在 HMTA 端全部成功（BLE→P2P→WS→download→status=1），但 OPPO 在下载请求后约 35ms 即回报 status=1；HMTA 收到后约 1 秒拆除 P2P 组，正在传输的数据被切断。
- 修复：发送端收到 status=1 后不再立即收工，先等待 `transferStartFuture`（下载请求到达）与 `transferCompleteFuture`（下载流真正写完），流失败时如实报失败；`/download` 增加文件清单与流状态日志，便于定位对端保存失败的真实原因。

> 注意：问题 3 的对端（OPPO）仍可能在流未写完时报成功，修复后 HMTA 会坚持传完再拆组；若流本身失败（如分享 URI 权限失效），HMTA 将显示失败而非伪成功。

### 0.5.2 第三轮回归（16:45 logcat 分析结论）

**问题 1（已修复，含 3 项体验优化）**：
- 后台接收确认页已能弹出；需优化项：
  1. 询问（接受/拒绝）应直接位于拉起前台窗口的通知上，而非窗口出现后再发第二条询问通知；
  2. 传输完成后窗口应自动关闭；
  3. 传输中窗口内取消键无效。
- 修复：
  - `P2pReceiverService` 收到 `sendRequest` 后，将拉起窗口的那条通知（`RECEIVE_CONFIRM_NOTIFICATION_ID`）原地更新为带接受/拒绝按钮的询问通知，同时广播 `ACTION_RECEIVE_ASK` 把发送者/文件名/大小同步到确认页窗口内直接显示接受/拒绝；
  - 确认页监听 `ACTION_RECEIVE_FINISHED` 后 `finish()`，广播改为 `setPackage` 显式投递，任务结束同时取消询问通知；
  - 取消键无效根因：`P2pReceiverService` 注册广播过滤器时漏了 `ACTION_CANCEL_RECEIVE_CONFIRM`，已补注册。

**问题 2（已修复）**：BLE disconnect+close 与三次重试生效，连续发送不再报蓝牙通讯失败。

**问题 3（根因定位并修复）**：
- 日志出现 `Permission Denial: opening provider ... not exported from UID 10241`：分享 URI 来自 MT 管理器，`ShareActivity` 结束后临时读权限失效，下载流打开失败 → 华为端提示"文件发送已中断"，OPPO 端显示成功但未落盘。
- 修复（第一版）：`ShareActivity` 点击接收者时打开 `ParcelFileDescriptor` 随任务传入服务 —— **实测崩溃**：Android 禁止 `startService` 的 Intent 携带文件描述符（`Not allowed to write file descriptors here`）。
- 修复（第二版，当前）：放弃 PFD，改为 `ShareActivity` 保持悬浮窗直到发送结束：点击接收者后页面显示"正在发送"+取消，发送服务结束后广播 `ACTION_SEND_FINISHED`，页面收到后自动关闭；期间分享 URI 的临时授权始终有效。

### 0.5.3 第四轮回归（17:03 修复）

- 问题 1 交互整理：去掉 `CATEGORY_CALL`（消除来电式胶囊/侧边收缩）；窗口内"取消/拒绝"立即关闭窗口并取消任务；接受后窗口显示"正在接收"，完成后自动关闭；通知始终复用同一条（拉起时"收到请求"+拒绝，询问到达后更新为接受/拒绝）。
- 问题 3 崩溃修复：撤销 PFD 传递（见上），改用"分享页保持悬浮窗至发送结束"。

### 0.5.4 第五轮（17:22，方案 2 决策落地）

- 决策：方案 1（保持前台窗口缩小为 1×1 像素 + 通知展示进度）在华为设备上不可靠——1 像素窗口属于系统重点检测的保活手段，EMUI/HarmonyOS 可能仍判定为后台导致 P2P 失败，且通知与隐形窗口的交互易出怪癖。故采用方案 2。
- 方案 2 落地：
  - 接收端：确认页窗口内显示进度条与已传/总大小（`ACTION_RECEIVE_PROGRESS` 广播驱动）；通知仅保留简单状态文字，不再展示进度。
  - 发送端：分享悬浮窗内显示发送进度条（`ACTION_SEND_PROGRESS` 广播驱动）；通知仅保留简单状态文字。
  - 通知按钮与窗口行为统一：接受/拒绝按钮改为 `PendingIntent.getActivity` 指向确认页（携带 action），由确认页在 `onCreate`/`onNewIntent` 统一处理并同步窗口状态，避免"点通知按钮后窗口不响应"的混乱；滑动删除通知仍走拒绝广播。

### 0.5.5 第六轮（17:33，接收窗口悬浮窗化）

- 接收确认页改为与发送流程同款的底部悬浮卡片：`Theme.Transparent` + 底部 35% 高度卡片（连接中/询问/接收中+进度三种状态同卡片内切换），`launchMode` 改 `singleTask`。
- 针对"传输完成后窗口只缩小为侧边图标"：去掉全屏来电式呈现（悬浮窗非全屏），并在 `ACTION_RECEIVE_FINISHED` 处理处增加日志，便于确认完成广播是否到达。

### 0.5.6 第七轮（17:42，进度条与通知交互修复）

- **接收窗口无进度条根因**：确认页广播过滤器漏注册 `ACTION_RECEIVE_PROGRESS`，进度数据未送达窗口；已补注册。
- 通知内容完善：拉起通知增加 `BigTextStyle` 说明（下拉展开可见完整指引）；询问通知展开显示文件名与请求详情，并设置 `setSilent(true)` + `setOnlyAlertOnce(true)`，避免窗口在前台时通知重复弹出打扰。

### 0.5.7 里程碑（17:50，整体验证通过）

- **OPPO→华为（后台接收）**：全屏通知拉起悬浮确认窗 → 询问/接受 → 窗口内进度条 → 完成自动关闭，全流程通过。
- **华为→OPPO（连续发送）**：BLE 断开释放后连续多次发送正常，不再需要重启对端分享服务。
- **系统分享面板**：分享页保持悬浮窗至发送结束，文件完整落盘，流程通过。
- **文本分享回归修复**：上一轮"等待下载流写完"逻辑会让文本分享（对端不发起 HTTP 下载）挂起 30 秒甚至卡死；已修复——仅文件传输等待下载流，文本分享直接结束。当前 fix8 已包含，待实机补测。

### 0.5.8 排查记录（20:20-21:00，发送/接收全面失败）

- 现象：fix12/fix13 及回退 fix10 后，发送与接收均提示"点对点连接建立失败"；系统自带 Wi-Fi Direct 也卡死在"正在与 OPPO 设备连接"。
- 日志证据：`WifiP2pService` 状态机所有建组/连组消息均落入 `DefaultState` 处理并返回 ERROR；`settings global wifi_p2p_on` 曾被置 0；`numPersistentGroup` 达 32。
- 结论：**华为系统"附近共享"服务（com.huawei.nearby）异常锁住 P2P**，系统级故障，与 HMTA 代码无关（fix10 同样失败、重启/清持久组/开 P2P 开关均无效）。
- 解决：`am force-stop com.huawei.nearby` + 重置 WiFi（`svc wifi disable/enable`）后，P2P 恢复正常，发送/接收恢复可用。
- 后续若复发：强制停止"附近共享"或重启手机。
## 1. 项目概况

HMTA 是基于 CatShare 的 Android 互传客户端，支持与 OPPO/一加等互传联盟设备进行文件传输。

| 类别 | 技术 |
| --- | --- |
| 语言/UI | Kotlin 2.3.10 + Jetpack Compose（Material 3） |
| 构建 | AGP 9.0.1 + Gradle 9.2.1，minSdk 29 / targetSdk 36 |
| 传输 | Ktor Server(Netty)/Client(OkHttp) + WebSocket + 自签名 TLS |
| 发现/握手 | BLE 广播与 GATT（nRF Kotlin BLE Client） |
| 组网 | WiFi Direct（5GHz/2.4GHz） |
| 提权 | Shizuku + AIDL 获取 MAC 地址 |
| 数据 | kotlinx.serialization、org.json（WebSocket 协议） |

## 3. 整体优化计划

> 优先级策略：先做低风险高收益的卫生清理与健壮性补强（阶段一、二），再做协议级能力（阶段三），安全加固穿插（阶段四），最后性能与工程化（阶段五、六）。每阶段完成后出 Debug APK 真机回归。

### 阶段一：代码卫生与工程基线（0.5-1 天）
1. 权限回调迁移 `registerForActivityResult`（问题 9）。
2. `ShizukuUtils` 阻塞等待改协程回调 + 超时（问题 10）。
3. 清理 `curreentTaskId` 拼写、`println()` 残留；`TextShareActivity` 决定接线或删除（问题 11）。
4. 移除 `MANAGE_EXTERNAL_STORAGE`、`ACCESS_BACKGROUND_LOCATION` 权限（问题 14、15）。
5. 内部广播改 `RECEIVER_NOT_EXPORTED`（问题 16）。

**验收**：Lint 无新增告警；权限列表精简；真机回归发送/接收/分享三流程不回归。

### 阶段二：传输健壮性补强（2-3 天）
1. 文本分享实机补测（fix8 已修）。
2. 5GHz 创建失败自动降级 2.4GHz（问题 4）。
3. 证书/密钥对进程级缓存（问题 5）。
4. 按 MIME 选择 Zip 压缩策略（问题 6）。
5. `HttpClient` 进程级复用（问题 19）。
6. 进度广播阈值节流（问题 21）。

**验收**：真机覆盖文本、多文件、大文件、弱网取消场景。

### 阶段三：传输协议增强（3-5 天，可与阶段二并行设计）
> **已取消（用户决定不执行）**：WebSocket 消息模型化、分块传输/断点续传/完整性校验均不再实施。保持当前协议与互传联盟/OPPO 系统端兼容。

### 阶段四：安全加固（2-3 天，穿插在阶段二/三之间）
> **已取消（用户决定不执行）**：TLS 证书指纹绑定、随机 IV 均不再实施，维持现有 TLS 自签名信任与固定 IV 方案。

**验收**：Release APK 体积下降 ≥20%，构建耗时下降。

### 阶段六：工程化与 CI（2-3 天）
1. 单元测试与传输冒烟测试（问题 22）。
2. CI 升级与拆分（问题 23）。
